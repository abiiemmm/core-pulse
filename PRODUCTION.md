# Production readiness

The objective remains a stable Windows app with a polished interface and complete features for monitoring, safe performance tuning, cleanup, and game troubleshooting. The current application is an internal build. Passing the checks below does not establish production readiness for the whole product.

## Implemented and checked on 2026-10-06

- Windows power control uses the native PowrProf APIs rather than a shell. Pending and restoration intent are durable before mutation; verification, rollback, external conflicts, and interrupted operations have fixture coverage. SQLite locks are released during OS calls. Active profile mappings cannot change, and the pending check is inside an immediate SQLite transaction.
- AC-only protection runs independently of monitoring pause or minimization. It owns only successfully activated sessions from the current runtime. Prior-launch recovery sessions remain visible for explicit review; automatic restore never forces an external scheme conflict.
- A bounded history queue separates live sampling from SQLite writes. Retention continues while monitoring is paused. Write, maintenance, and overflow errors surface as a degraded storage status; successful writes recover it. Purge invalidates queued samples so deleted history cannot reappear. A fresh database reserves the logical device in the sample transaction, so history can save before GPU discovery finishes. Settings display the last saved sample and skipped samples since launch.
- Slow GPU identity discovery runs after startup on a background worker. The fixed PowerShell discovery command is hidden, uses the system executable/module path, bounds output, and terminates its job on timeout. Live metadata is available even if its database save fails.
- The new read-only Processes page provides CPU normalized to all logical cores, resident memory, PID, executable path when readable, search, sorting, pagination, refresh, and pause. It samples only while the page is open and visible, caps snapshots at 2,048 rows, and renders warmup/restricted readings as unavailable. It exposes no process termination command.
- The official Tauri single-instance plugin is pinned to 2.4.0. A second launch shows, restores, and focuses the existing window. The existing Tauri 2.11.6 framework and matching transitives remain pinned in the Rust lockfile. See the [Tauri single-instance contract](https://v2.tauri.app/plugin/single-instance/).
- The current Rust suite passes 91 tests with the pinned single-instance dependency. The frontend production and native debug builds, 35-command IPC registration, schema, analytics, localization and sole-maintainer repository checks pass. The previous native checks cover all nine pages in three languages at 1440 × 860 and 860 × 610, all analytics ranges, themes and preference persistence. The process viewer uses actual Windows readings; storage-notice events are simulated, while isolated Rust fixtures exercise real database failures. Evidence is under `artifacts/stability/` and `artifacts/redesign/feature-verification.json`.
- Native second-launch verification confirms exit code 0, the original process retained, and exactly one app instance. The standalone release loads `http://tauri.localhost/` without a development server; CPU/RAM/disk/network remain supported.
- The unsigned current-user NSIS installer passed fresh installation, same-version reinstallation, and silent uninstall with an unelevated Windows token. All three existing SQLite files retained identical hashes at each stage. The fixture installation and its registry preferences were removed. Cross-version upgrades and broader hardware/account coverage remain open.

## Historical checks on 2026-10-05

- The existing desktop redesign provides seven pages, persistent light/dark/system themes, Indonesian/English/Spanish, keyboard navigation, and retained analytics. That historical review has since been superseded by the nine-page native review.
- The cleaner now resolves its allowlist from the current user's Windows known folder, rather than trusting `TEMP`. It rejects a redirected Temp directory and accepts no arbitrary paths from IPC.
- The scan records the volume and 128-bit file ID. Cleanup compares identity, metadata, link count, and final path through an exclusive file handle, then requests deletion through that same handle. Directory handles pin the allowlist and parent chain until deletion completes.
- Cleaner regressions cover old/new files, locked/changed files, same-size/same-timestamp replacement, hard links before/after scanning, junction redirection before/after preview, parent/ancestor swaps, cancellation, expired/replayed plans, replaced roots, and read-only deletion errors.
- Cleanup sends bounded progress events with an opaque plan ID and counters, without private paths. The UI ignores unrelated events, prevents repeated cancellation, retains the last outcome, and invalidates consumed scans even after a command error. Failed files do not also inflate the skipped count.
- SQLite retention aggregates whole minutes and merges delayed samples using weighted averages. Aggregation, raw deletion, and retention maintenance are atomic. Tests verify repeated maintenance, rollback after injected failure, expired history removal, and preservation of unfinished power recovery sessions.
- `npm run check` passes: 18 Rust tests, IPC registration, schema/foreign keys, analytics and translation checks. The frontend production build passes.

- A registry-backed npm lockfile pins resolved dependency versions and integrity hashes. Windows CI uses `npm ci` and also checks analytics/translations.
- A clean `npm ci` installation, production frontend build, and `npm run check` succeeded. `npm audit --json` reported zero known advisories at the time of this check; this is a point-in-time result, not a security guarantee.
- `npm run tauri:build` produced a Windows x64 NSIS internal installer. The release executable opened at `http://tauri.localhost/` with the Vite server stopped; the cleanup UI checks above also passed using the bundled release assets. The Windows deletion implementation follows the documented [SetFileInformationByHandle disposition contract](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle), [final handle path API](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew), and [Windows known-folder lookup](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shgetknownfolderpath).

## Sensor integration evidence

- The isolated host pins LibreHardwareMonitorLib 0.9.6 and .NET SDK 10.0.401, restores a checked-in NuGet lockfile, and publishes a self-contained Windows x64 runtime. The bundle includes original source archives, license notices, host rebuild sources, and hashes for corresponding source revisions. No driver installation, elevation request, fan-control setter, or arbitrary frontend command is exposed.
- The protocol distinguishes measured zero from missing values, validates device/sensor identity, unit, range, sequence, timestamp, version, and maximum frame size, and clears retained readings before updates. Duplicate upstream sensor IDs are disambiguated by a deterministic name hash. CPU temperatures are intentionally withheld because fresh-looking upstream zero values can represent failed driver access.
- Sampling and sensor recovery run separately. A Windows job contains the host; crashes, malformed data, and timeouts terminate its process tree. Restart delays grow from 1 to 60 seconds. Old cached values become unavailable, and pausing monitoring releases the host after ten seconds. Fixture tests cover these boundaries, and raw/retained analytics tests verify isolation between GPU adapters.
- Native verification on the Ryzen 7 5800H hybrid laptop uses AMD Radeon integrated graphics and an NVIDIA RTX 3070 Laptop GPU. It checks actual readings, exact adapter selection, selection while paused, invalid-ID rejection, helper interruption/recovery, continued basic monitoring, and three-language sensor controls at regular and compact sizes. NVIDIA temperature and both adapters' usage are available; AMD and CPU temperature remain unavailable on this configuration. See `artifacts/sensors/native-verification.json`.
- The per-device provider ID also constrains persisted GPU history and analytics. Frontend histories reload on selection and discard responses for previous selections. Automatic selection prefers NVIDIA on hybrid laptops, then AMD, then other adapters; the saved selection can override this. GPU temperature prefers a package/core sensor and otherwise uses the hottest reported temperature, which the UI explains.
- A token-handle leak found during the short observation was fixed by disposing WindowsIdentity after each permission check. The host self-test now checks 250 repeated permission calls, and 50 real sensor updates retained exactly 286 handles after warmup. This is a short regression observation, not a sustained resource budget. See `artifacts/sensors/handle-lifetime-verification.json`.
- The final unsigned sensor installer passed current-user installation, same-version reinstall, and uninstall without elevation. All 235 bundled sensor/runtime/source/notice files matched the prepared bundle, the installed host self-test passed, and all three existing SQLite file hashes stayed unchanged. See `artifacts/sensors/installer-verification.json`.
- A second native launch retained one application and one sensor child. Closing the final QA app also terminated its sensor child. The final 30-second resource observation is recorded separately and excludes WebView2 processes, so it is not a full application memory or long-run budget.
- The current sensor check does not establish CPU-driver support, a sustained resource budget, physical AC transitions, cross-version upgrades, full release licensing/signing, or coverage across desktop/AMD/Intel/NVIDIA combinations. Those remain part of the active product goal.

## Gaming registration and identity evidence

- Gaming adds a ninth page with native file selection, registration/edit/removal, stored profile preference, and verified running-process counts. It does not launch or terminate games, and registration never arms Auto Boost. The automatic controller, runtime worker and opt-in UI are now integrated; their full native FR-06 lifecycle verification remains open.
- File selection is restricted to a native Rust-owned dialog using the official pinned Tauri dialog plugin 2.7.1, compatible with the existing Tauri 2.11.6. Frontend filesystem and generic dialog permissions remain disabled. Parent handles are resolved on the window thread; the picker returns through a callback while executable validation runs on a worker.
- Registration accepts a one-use, five-minute selection token. It rechecks a local Windows PE executable, canonical handle-derived path, volume/file ID, file size, and last-write time. Unknown tokens, changed/replaced files, duplicate physical executables, and invalid names/profiles are rejected. Game names and executable paths remain local; activity logs contain generic registration/removal summaries.
- Process names only narrow the candidate list. A held limited-access process handle, creation time, canonical image path and executable identity prove a match. Existing verified handles remain until their process actually exits; same-name executables elsewhere do not match. Discovery is bounded to 8,192 processes and cached for two seconds. Partial or unreadable identity is shown explicitly rather than treated as a match.
- SQLite schema version 2 adds registered-file identity, archival state and indices. A captured schema-version-1 fixture verifies migration preserves preferences, prior gaming history and unfinished tuning recovery, disarms legacy registrations lacking verified identity, and refuses future schemas without resetting data. Removal keeps registrations referenced by session history and deletes unused registrations without deleting executables.
- The registration baseline passed 64 tests, including real Windows same-name/different-path process fixtures, two concurrent matching processes, one/final exit, expired/replayed tokens, file replacement, edit/removal and database migration. Frontend build, analytics/translations, 31-command IPC registration and SQLite checks pass.
- The native development database migrated from schema 1 to 2 with preferences, profile mappings and tuning recovery records preserved. Foreign-key checks passed and QA registrations were removed. Evidence is in `artifacts/games/migration-verification.json`; installer upgrades remain a separate release check.
- Native Gaming QA passed 24 checks, including actual picker cancel/select, persistent registration, token rejection, two matching processes, removal while a process continues running, three languages, dark/light themes, normal/compact layouts and modal keyboard isolation. The actual Windows power GUID stayed unchanged. Evidence is `artifacts/games/native-verification.json`; these checks prove registration and matching, not automatic tuning or FPS capture.

## Integrated Auto Boost runtime

- `automation.rs` implements one global tuning owner, durable gaming sessions and links, deterministic profile selection, overlap/final-exit policy, AC protection, explicit-restore suppression, outside-change conflicts, restart recovery and policy-aware shutdown. `power.rs` commits pending intent and gaming links atomically before a game-owned scheme change.
- `automation/runtime.rs` runs independent discovery/protection workers, stores one latest observation, rejects expired or configuration-invalidated data, and rechecks current eligibility and held process liveness immediately around pending intent. File inspection stays outside the automatic operation lock. Configuration and manual restore serialize with controller decisions; blocked discovery does not delay AC protection or shutdown restoration.
- Typed opt-in/status/history commands and the Gaming UI add explicit enable confirmation, AC/restoration rules, translated status explanations, manual-recovery navigation and the latest 50 local session summaries. Completed-summary deletion preserves hardware samples and power recovery. Registration remains disarmed until explicitly enabled.
- `npm run check` passes 91 Rust tests, including 19 controller fixtures and five new runtime fixtures, plus ownership, analytics/translations, 35-command IPC registration and SQLite checks. Native-process runtime fixtures prove multiple-instance/final-exit handling, AC/manual restoration and shutdown while discovery is blocked, stale/generation invalidation and final liveness checks. Power operations in these fixtures are simulated; the actual Windows power scheme is untouched. The frontend production and native debug builds pass.
- Native UI verification of the new controls/history, actual scheme-change lifecycle, physical AC transitions, sleep/resume and sustained resource behavior remain required. The previous nine-page/Gaming screenshots predate these controls. See [docs/AUTO_BOOST.md](docs/AUTO_BOOST.md). This checkpoint does not establish production readiness or complete FR-06.
